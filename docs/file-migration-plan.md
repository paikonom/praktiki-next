# Σχέδιο μεταφοράς παλιών PDF

## Βασική αρχή

Κανένα αρχείο της παλιάς εφαρμογής δεν μετακινείται, μετονομάζεται ή
διαγράφεται κατά την ανάλυση. Η μεταφορά γίνεται μόνο με αντιγραφή και είναι
πλήρως επαναλήψιμη.

## Σημερινή σύνδεση

Για τα περισσότερα αρχεία η σύνδεση είναι ντετερμινιστική:

```text
students.sid
    -> states_student.<document_code>
    -> filesTable.fileName = <document_code>
    -> uploads/<sid>/<sid>_<document_code>.pdf
```

Παράδειγμα:

```text
sid = 1234
document_code = symf_SN_FULL
path = uploads/1234/1234_symf_SN_FULL.pdf
```

## Βήμα 1 — Read-only inventory

Δημιουργείται manifest για κάθε παλιό PDF με:

- legacy SID,
- document code από το filename,
- πλήρες παλιό path,
- μέγεθος,
- SHA-256 checksum,
- modified timestamp,
- αντίστοιχη τιμή από `states_student`,
- αντίστοιχη εγγραφή από `filesTable`,
- αποτέλεσμα ελέγχου PDF.

Το manifest είναι αναφορά. Δεν αλλάζει την παλιά βάση ή τα αρχεία.

## Βήμα 2 — Reconciliation

Παράγονται ξεχωριστές λίστες για:

- state = 1 και αρχείο υπάρχει,
- state = 1 αλλά αρχείο λείπει,
- state = 0 αλλά αρχείο υπάρχει,
- αρχείο με άγνωστο document code,
- αρχείο με SID που δεν υπάρχει στη βάση,
- διπλότυπα αρχεία ή ίδιο checksum,
- filenames που δεν ακολουθούν το κανονικό pattern,
- κατεστραμμένα ή μη έγκυρα PDF.

Οι εξαιρέσεις επιλύονται ή εγκρίνονται πριν από το production cutover.

## Βήμα 3 — Legacy ID mapping

Κατά τη μεταφορά της βάσης αποθηκεύονται μόνιμες αντιστοιχίσεις:

```text
legacy_students.sid -> new_internships.id
legacy_students.uuid -> new_internships.legacy_uuid
filesTable.fileName -> document_types.code
```

Δεν βασιζόμαστε στο ότι τα νέα IDs θα είναι ίδια με τα παλιά.

## Βήμα 4 — Copy αρχείων

Για κάθε έγκυρη γραμμή του manifest:

1. Βρίσκεται η νέα πρακτική μέσω του legacy SID mapping.
2. Βρίσκεται ο νέος τύπος εγγράφου μέσω του παλιού document code.
3. Δημιουργείται η νέα λογική εγγραφή document.
4. Το PDF αντιγράφεται στη νέα ιδιωτική αποθήκευση.
5. Υπολογίζεται ξανά SHA-256 στη νέα θέση.
6. Η αντιγραφή γίνεται αποδεκτή μόνο αν τα checksums είναι ίδια.
7. Δημιουργείται document version με ένδειξη `legacy_import`.
8. Καταγράφεται migration audit record.

## Βήμα 5 — Verification

Μετά από κάθε δοκιμαστική μεταφορά ελέγχονται:

- συνολικό πλήθος αρχείων,
- συνολικό μέγεθος,
- πλήθος ανά document code,
- πλήθος ανά ακαδημαϊκό έτος,
- πλήθος ανά νέα πρακτική,
- checksum κάθε αρχείου,
- εγγραφές χωρίς αρχείο,
- αρχεία χωρίς εγγραφή,
- τυχαίο οπτικό δείγμα από εξουσιοδοτημένο χειριστή.

Η μεταφορά δεν θεωρείται επιτυχής μόνο επειδή το script ολοκληρώθηκε.

## Συχνές νέες αλλαγές πριν το cutover

Επειδή η παλιά εφαρμογή συνεχίζει να δέχεται uploads:

1. Γίνεται αρχική πλήρης δοκιμαστική μεταφορά.
2. Οι επόμενες δοκιμές αντιγράφουν μόνο νέα ή αλλαγμένα checksums.
3. Λίγο πριν το cutover η παλιά εφαρμογή μπαίνει προσωρινά σε read-only mode.
4. Εκτελείται τελικό delta scan βάσης και filesystem.
5. Γίνεται τελικό reconciliation.
6. Ενεργοποιείται η νέα εφαρμογή.

## Τι δεν μπορεί να ανακατασκευαστεί

Όταν ένα παλιό upload αντικατέστησε το προηγούμενο PDF στο ίδιο path, το
προηγούμενο αρχείο δεν μπορεί να ανακτηθεί από το τρέχον filesystem, εκτός αν
υπάρχει σε παλιότερο backup. Στο νέο σύστημα όλες οι επόμενες αντικαταστάσεις
θα δημιουργούν νέα version.

## Παλιοί σύνδεσμοι

Το legacy UUID και το document code μπορούν να διατηρηθούν για μεταβατική
συμβατότητα. Παλιό link μπορεί να οδηγεί σε ελεγχόμενο compatibility endpoint,
χωρίς το νέο φυσικό path να μοιάζει με το παλιό.
